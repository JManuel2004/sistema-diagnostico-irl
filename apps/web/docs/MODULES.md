# Web Features

Deliberately short. What can be derived from the code is not documented by hand: the folder tree is `apps/web/src/features/`, and the routes are in the router. This file states the rule and maps each feature to the backend module it talks to.

This is the frontend counterpart of [`apps/api/docs/MODULES.md`](../../api/docs/MODULES.md). Where the backend organizes by NestJS module = bounded context, the frontend organizes by **feature folder = bounded UI capability**.

The rule that overrides everything else: **features cannot import from other features**. ESLint enforces it via `eslint-plugin-boundaries`. Cross-feature reuse goes through `shared/`; cross-tier contracts go through `@innlab/contracts`.

## Features that exist

| Feature | Talks to (backend) | Page |
| --- | --- | --- |
| `auth` | `shared/identity` — INNLAB SSO session and the user's profile (`me/context`): `UserMenu`, `UserContextGate`, `useCurrentUser` | `AuthCallbackPage`; the header of every page; `StartDiagnosticPage`, `DashboardPage` |
| `questionnaire` | `diagnosis` — questionnaire structure; the draft of the 48 answers and their optional justifications (Zustand); the summary table | `DiagnosticWizardPage` (steps 3 and 4) |
| `consent` | `initiative` — the current consent text (served by the backend) and recording a new acceptance of an initiative (Law 1581) | `DiagnosticWizardPage` (step 1) |
| `initiative` | `initiative` — the user's initiatives (list, create with the first acceptance, `InitiativeChooser`), profile registration and reading, sector and stage catalogs; the browser draft of steps 1 and 2 | `DiagnosticWizardPage` (step 2), `InitiativePage`, `DashboardPage` |
| `maturity-profile` | `diagnosis` — profile | `ResultsPage` |
| `portfolio-recommendation` | `diagnosis` (accepts deep analysis) and `routing` (reads the recommendation and its trace) | `ResultsPage` |
| `scaling-roadmap` | `roadmap` — reads the saved roadmap | `ResultsPage` |
| `report` | `reporting` — reads the full report, shows what only it has (initiative, level meanings, the 48 answers as `ReportAnswers`, attribution), downloads it as a PDF (`DownloadReportButton`) and offers it from the results (`FullReportCard`) | `ReportPage`, `ResultsPage` |

There is no `diagnostic` feature: starting, reading and processing a diagnostic go through `shared/api/diagnostic.api.ts` and `shared/hooks/`, because several pages and features need them.

## Pages and flow

`/` (landing, public, no navigation, one button) → **Iniciar diagnóstico** → `/panel` (protected: without a session it goes through the INNLAB sign-in and continues there on return; the sign-in lands on the panel when there is no route to return to) → the completed diagnostics to consult or **Iniciar diagnóstico** → `/diagnosticos/nuevo`, which asks the backend for a **new** diagnostic (its unfinished ones are deleted) → the wizard `/diagnosticos/:id/asistente/:step` (no navigation) → `/diagnosticos/:id/resultados` (the first screen with navigation) → `/panel`. Once the deep analysis is complete, the results lead to `/diagnosticos/:id/reporte`, the full report.

The wizard has four steps, in this order: `consentimiento` (privacy consent, before any initiative data), `iniciativa` (choose one of the user's initiatives or a new one, and its profile), `cuestionario` (48 statements, each with an optional justification) and `resumen` (a table per dimension, in tabs, with **Statement / Score / Justification**; «Procesar diagnóstico» sends the answers and computes the profile). Which step applies is decided by what the server already has (the diagnostic's initiative profile, only registered with a current consent) and, before that, by whether the current text was accepted in this tab: resuming lands on the first missing step and a later step cannot be opened by URL. A diagnostic that already has results is not resumed: its results open.

- **The consent comes first** ([ADR 0015](../../../docs/architecture/decisions/0015-consent-before-the-initiative.md)) **and belongs to the initiative** ([ADR 0011](../../../docs/architecture/decisions/0011-initiative-identity-and-consent-per-initiative.md)). Step 1 shows the text served by the backend and keeps only the accepted version in the browser draft (`useInitiativeDraftStore`, `sessionStorage`). Step 2 records that acceptance on the chosen initiative (creating a new one with it, or a new acceptance of an existing one) and then registers the profile; an initiative that already accepted the current text only registers the profile. The backend refuses a profile without a current consent (409), and the wizard goes back to step 1.
- **Calculations show their reasoning** (`ProcessingState`): processing the diagnostic and calculating the deep analysis show, step by step, what the system works out, for at least `PROCESSING_VISIBLE_MS`; the step icon only spins when the user allows motion. Retrying the deep analysis shows a single wait for both results.
- **The questionnaire is the diagnostic's framework version**: steps 3 and 4 and the results ask for `catalog/questionnaire?version=<Diagnostic.frameworkVersion>`.
- The old `/perfil`, `/recomendacion` and `/roadmap` routes redirect to `/resultados`; `/cuestionario` and `/consentimiento` redirect to their wizard step; `/diagnosticos` redirects to `/`.
- `/panel` shows the initiative of the latest diagnostic **with results**, offers to continue one still in the wizard, and reserves the space for the history of past diagnostics (a future story). `/diagnosticos/:id/iniciativa` is only for correcting an already registered initiative profile, and only while the deep analysis is not accepted (afterwards it says the profile is frozen, and the panel hides «Editar iniciativa»); the first registration is wizard step 1.

### The user's profile (HU-01, HU-25)

- **Where it comes from:** an access token from the shared pool carries only the `sub`, with no email or name. `useCurrentUser` therefore asks this system's backend (`GET /me/context`), which asks INNLAB Core, the owner of that data. The response is validated against `meContextResponseSchema` in `@innlab/contracts`, and the backend controller is typed with the same contract, so a drift fails at compile time.
- **`UserMenu`** is the header's only account control: an avatar (the initial of the name, or of the email) that opens a dropdown with name, email and «Cerrar sesión». If the profile does not arrive it simply does not render.
- **`UserContextGate`** withholds what needs to know who the user is. Starting a diagnostic, above all: a diagnostic belongs to whoever starts it. It wraps the request on `/diagnosticos/nuevo` and the panel's «Iniciar diagnóstico». If Core cannot be reached it says the service is temporarily unavailable and offers a manual retry, instead of creating a diagnostic nobody can claim.

## Where things live

- **Server state → React Query; UI/draft state → Zustand**, never both for the same piece of state — see [`STATE_MANAGEMENT.md`](./STATE_MANAGEMENT.md).
- Each feature owns its API module under `features/<name>/api/`; calls shared by several features live in `shared/api/` (for example `diagnostic.api.ts`).
- **One results page.** `ResultsPage` shows the maturity profile and, only when the backend says the deep analysis was accepted (`deepAnalysisAccepted` on `GET diagnostics/:id`), also the imbalanced pairs, the critical-state alerts, the recommendation and then the roadmap (the recommendation opens the route, so it is shown first). The accept button (`AcceptDeepAnalysisCard`) lives in that page; nothing is sent by merely opening it. The recommendation and the roadmap are not even requested before acceptance.
- Pages compose features: `ResultsPage` uses four (`maturity-profile`, `scaling-roadmap`, `portfolio-recommendation`, `report`) and `ReportPage` the same four plus `questionnaire` (what each dimension measures); a feature may not import another, a page may.
- **The full report** (`ReportPage`, HU-23, [ADR 0018](../../../docs/architecture/decisions/0018-report-gathered-from-saved-results.md)) exists only when the backend says the deep analysis is complete (`deepAnalysisCompleted` on `GET diagnostics/:id`, both results saved): only then the results show `FullReportCard` and the page requests `GET diagnostics/:id/report`. Without it, or on a `409 REPORT_NOT_AVAILABLE`, the page says the report is only available after completing the deep analysis. It is as interactive as the results and reads from the report's single response: the page composes the sections only the report has (`report`: the initiative, the global level and what each level means, the answers, the attribution) with the interactive pieces of the results — the radar and its shared highlight (`ProfileOverview`), the pairs and alerts (`ImbalanceInsights`), the service (`RecommendationSummary`) and the route with «Al terminar la ruta» (`RoadmapPhaseList`) — under a sticky section bar like the results'. **The 48 answers** (`ReportAnswers`) read at a glance as a 6 × 8 grid, one hue from light (1) to dark (5) (`PALETTE.likert`, checked as an ordinal ramp) with the number in every cell, a spelled-out scale, and a tooltip with the statement; a click opens the dimension's tab and marks the statement, where each answer shows five segments, its words and the justification. On a phone the row labels are cut so the eight cells stay on screen. «Descargar reporte (PDF)» (HU-24) is the page's primary action and appears only with the report loaded: without the deep analysis complete there is no download option anywhere. The file comes from `GET diagnostics/:id/report/pdf` through `getFile` (`shared/api/http.ts`, the session's token like every call; a plain link could not carry it), is saved under the name the server suggests (CORS exposes `Content-Disposition`), and the outcome is a toast; a 409 says the report is only available after the deep analysis.
- **The radar, its legend and the summary cards share one highlight** (`useRadarHighlight`, local state of the page, no global store): hovering or focusing a card, a legend item or a pair highlights its dimensions in the radar; a click on a legend item pins it. The highlight flows back too: the signal card that points at the highlighted dimensions stands out and the other cards and level rows fade, whether the cursor is on the radar, a card or a level.
- **Starting a diagnostic** is `POST diagnostics` (`useStartDiagnostic`), always a new one: the backend deletes the user's unfinished diagnostics. `StartDiagnosticPage` and the panel use it and open the wizard, which decides the step. A diagnostic in progress is continued only from the tab that holds its draft: the panel reads the owner of the questionnaire and initiative drafts and offers «Continuar diagnóstico» while that diagnostic is not `completed` (DIAGIRL-26). `completed` on the diagnostic (derived by the backend) tells a diagnostic with results from one still in the wizard.
- **The questionnaire does not scroll on mount.** `DimensionTabs` scrolls to the top of its panel only when the dimension changes (compared with the last shown), so the page loads from the top, also under StrictMode; every wizard step opens from the top of the page.
- **Development autofill.** `src/dev/` holds the AgroConecta case (initiative profile and the 48 answers with their justifications) and two buttons. They exist only when `VITE_DEV_AUTOFILL` is `true` **at build time**, which only `.env.development` sets; a production build does not contain the data or the buttons (`src/dev/__tests__/production-bundle.test.ts` builds and checks). The backend e2e suites use the same 48 scores (`apps/api/test/e2e/support/agroconecta-case.ts`).
- **Typecheck.** `pnpm typecheck` and `pnpm build` run `tsc -p tsconfig.app.json`; the bare `tsc --noEmit` at the root checked nothing because that tsconfig only has references.
- **The frontend keeps no dimension names.** `name` and `shortName` come from the responses that name dimensions (profile, roadmap) and from the questionnaire catalog; only the visual metadata (colors, order) lives in `shared/lib/dimensions.ts`. The public landing page keeps its own editorial copy.

## Results page: how it reads

- **The page opens with the initiative** (`ProfileHero`): its name as the page title, a short description (the product type) and its sector and stage as badges, and next to it the global IRL level (RF-09, the simple average of the six levels, computed by the backend as `globalAverage`) with what that level means (`globalLevel`, the average rounded half up) and the strongest and the weakest dimension. The sections then address the initiative by name.
- **Every score with its meaning** ([ADR 0017](../../../docs/architecture/decisions/0017-level-descriptions.md)): the radar names each point by its code (TRL, TmRL…) and its tooltip gives the dimension's name, what it measures, the level and «Estar en el nivel N significa: …» (`levelDescription`); there is no separate list of levels. The global level's meaning (that of the whole level the average rounds to) is a tooltip over the score itself, with no extra chip that could read as a second number. Each roadmap target says what reaching it means (from the profile's `levelScale`).
- **No radar legend.** Each point of the radar has the color of its dimension and, on hover or keyboard focus, a tooltip that says what the dimension measures (the description comes from the questionnaire catalog) and its level. The emphasis (a hovered point or card fades the rest) is CSS driven by a `data-highlighted` attribute on the radar wrapper (`globals.css`, «Radar emphasis»), and the chart itself is memoized: re-rendering recharts on every hover restarts its animation and remounts the points, which closes the tooltip under the cursor.
- **The deep analysis is written for someone who knows neither the system nor the IRL framework:** dimension names instead of codes, sentences instead of arrows or symbols, no internal identifiers (the trace and the roadmap explanation say what an adjustment did and why the center declared it, never its code), and no reading text below `text-sm`. Imbalances are ordered by severity; pairs, alerts, roadmap and service are white cards with hairlines, and only the critical pair, the recommended service and each phase's service carry a coloured top line. Critical dimensions get their own card with the next step from the roadmap. A service an adjustment of the center put into the ranking has no score: if it is an alternative, the card says the center suggests it, with the reason; the trace panel says in which place it entered. Once the deep analysis is accepted, a sticky section bar reaches its four blocks (Perfil, Desequilibrios y alertas, Servicio INNLAB, Roadmap) and, like the header navigation, marks the one being read with a blue underline on top of `aria-current` (`useActiveSection` follows the scroll).
- **The routing trace answers before it explains** (`LayerTracePanel`): one sentence says which service came first and why, then three steps — what does not apply, the order, the center's adjustment. When an adjustment applied, step 3 shows each one with its declared reason and then the order it left, marking the services an adjustment moved or included; the «Recomendado» mark goes to the first of that order, not to the first of the calculation. Only the winner shows its reasons, as labels; the rest fold away. A label that groups several dimensions always says which ones: «3 brechas» names them in its tooltip and repeats them in a `sr-only` text, so the count is checkable without a pointer.
- **The roadmap is a route of services** ([ADR 0016](../../../docs/architecture/decisions/0016-route-by-phases-with-services.md)): each phase (`RoadmapPhaseCard`) opens with the service that could be contracted for it, its card and «¿Por qué este servicio?» (told from the phase's trace: the recommendation opens the route, or how the service works the phase's dimensions), or says plainly when none fits and the closest one is shown. Each dimension shows the levels this phase covers; a rise split across phases says it continues. The list closes with «Al terminar la ruta» (`RoadmapEnding`): the imbalances with an alert, the global level and how many dimensions go up, today against the end; each dimension on the 1–9 scale with where it is today and where the route leaves it; and the six pairs with their difference today (classified by the profile) and at the end. Hovering a pair leaves only its two dimensions lit. Nothing is classified in the frontend: the end is told by the roadmap's `balanced`.
- **The invitation to the deep analysis** (`AcceptDeepAnalysisCard`) is a proposal with two paths, ask for it or continue later from the panel; it sends nothing until the user asks. The deep analysis is a paid feature: its card is a solid brand block with white text, a «De pago» badge and a dollar mark, and its button reads «Adquirir análisis profundo». It makes no claim about the payment itself (gateway, security, refunds): no payment flow exists yet.
- **Every service shows its card** (`shared/ui/service-details.tsx`, `ServiceDetails`): its subtitle, its tier and its band as chips with their icon (`shared/ui/chip.tsx`): «Nivel: Descubre», told in words, never by a color, whose tooltip gives the tier's promise and description from the catalog (`service_tier.tagline` and `description`), and «IRL global 3 a 5», whose tooltip gives the band in a sentence, «¿De qué se trata?» and «Qué puede lograr», all from the catalog. The recommended service (`RecommendationSummary`) shows it whole and offers «Solicitar acompañamiento»; each alternative keeps it behind «Ver ficha»; each phase of the roadmap shows its service's card. The request flow is not defined yet: without an `onRequestService` handler the button is disabled and announced as coming soon.

## Design system (`shared/ui`, `shared/lib`)

Brand and visual rules are in `DESIGN.md`, kept next to the repository (not inside it). Two of them decide most of what follows, both measured on <https://innlab.org>: **colour is a budget** (its interior pages keep 90% of the area white or light grey and spend accent colour on 1–5%), so here colour rides on the data (bars, radar, dimension icons), on one brand mosaic per screen, on the primary button and on the footer; and **corners are straight** everywhere except circles. What the code offers so no screen writes its own:

| Piece | Use |
| --- | --- |
| `shared/lib/palette.ts` | **Single source of the brand, semantic and dimension colors.** `tailwind.config.ts` imports it to build the utilities and SVG code (the radar) reads the same constants. Surface, text and border tokens are HSL variables in `styles/globals.css` (`hsl(var(--border))` in SVG). Never write `var(--color-…)`: no stylesheet defines it. |
| `Card` | Content box: straight corners, hairline border, no shadow. |
| `ServiceDetails` | The card of a portfolio service (its tier and band as chips explained in their tooltips, «¿De qué se trata?», «Qué puede lograr»), the same in the recommendation, its alternatives and each roadmap phase. |
| `Chip` | A short attribute with its icon (a tier, a band, a difference); with `info` it is a button that explains itself in a `Tooltip`. Sentence case, unlike `Badge`, which labels a status. |
| `ProcessingState` | What a calculation shows while it runs: the steps it works out, one after another, at least `PROCESSING_VISIBLE_MS`; the step icon spins only with `motion-safe`. |
| `Alert` | State message (error, notice, info, confirmation) with icon and ARIA role; `critical` is `role="alert"`. Not a `Card`. |
| `LoadingState` | The one loading treatment. The questionnaire skeleton stays apart because it reproduces the shape of the 48 cards. |
| `PageHeader` | Overline, `text-h1` title, description, and optional metadata below. |
| `ResultMeta` | «Resultado guardado el …», under the title of profile, recommendation and roadmap. |
| `DisclosurePanel` | Collapsible «how we got here» panel (recommendation trace, roadmap explanation). |
| `AcceptDeepAnalysisCard` | The invitation to accept deep analysis, on the results page and for retrying a calculation that failed. |
| `SectionHeader` | Title of a section inside a page (`h2`), with its description, its result metadata and, optionally, an icon inside a blue circle. |
| `Tooltip`, `GlossaryTerm` | One-sentence explanations of the technical terms (`shared/lib/glossary.ts`), reachable by hover and by keyboard (Radix). |
| `Field`, `Input`, `Textarea`, `Select` | Form controls with label, hint and error wired with `aria-describedby`, from the `DESIGN.md` form input: 48px high, 16px text so mobile browsers do not zoom in, and `Select` is still a native `<select>` with its own chevron. `Textarea` grows with its content: a long answer is read whole, with no scrollbar inside the field. |
| `AppNav` | Navigation after the institutional descriptor: panel and results of the active diagnostic (the one in the URL, else the latest with results). Only on the screens after the wizard (results, panel, correcting the initiative); opt-in per page (`PageShell showNavigation`). |
| `BrandDescriptor` | The institutional descriptor; it links to `/panel` whenever there is a session (the wizard included) and to `/` (the landing) without one. |
| `Badge`, `LevelBar`, `DimensionChip` | Small pieces that make a result readable at a glance: a labelled category or severity (`Badge`, an uppercase 14px label over a soft wash of its tone), the 1 to 9 scale as nine segments with an optional goal and gap threshold (`LevelBar`), and a dimension with its icon and color (`DimensionChip`). The icon, `bg`, `chip`, `tint`, `border` and `fill` of each dimension come from `getDimensionVisual` (`shared/lib/dimensions.ts`); `tint` is neutral, so a dimension is told by its icon, its text and its bars. |
| `WizardStepper` | The steps of the wizard and the current one (number or check, `aria-current="step"`); earlier steps are links, later ones are not. Under `sm` the list becomes «Paso N de M» with a segment bar: four steps do not fit in a 390px row. |
| `notify` | Toasts for the outcome of an action (`notify.success`, `notify.error`), over Sonner. Errors while loading a screen stay inline, as `Alert`. |
| `PageShell` | The chrome of every page: institutional descriptor, navigation (opt-in) and the blue footer with the Icesi | INNLAB lockup and the KTH attribution. Under `md` the navigation drops to its own tab row and the side gutter is 16px. |
